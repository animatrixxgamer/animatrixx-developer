Live Case study · School platform

A school website and the software behind it, in one system.

Temidire International College in Ondo Town needed two things that usually become two projects: a public website parents can read, and the management software the office runs on every day. They share one database, one login and one deployment.

The brief

Four problems a school office already has.

A school does not need a website and a management system as separate purchases. It needs the admissions form to end up in the same place as the pupil's invoice, the register to feed the same term the report card prints, and a parent to be able to check a balance without calling the office at break time.

So the work was scoped as one system, with three audiences inside it: the public, the staff, and the student or parent. Everything below is what that system actually does today, plus a plain list of what it doesn't.

What it does

Three sides of the same school.

Grouped by who signs in, because that is how the software is organised.

Everyone · no login

The public website

  • School pages for about, academics, school life, transport, news, gallery and contact
  • A four-step admissions application that writes straight into the staff pipeline
  • A staff directory and leadership page filled from the database, not a static list
  • News, events and announcements published once and shown on the public site

Staff · role-based login

The admin dashboard

  • Applications, the student roll, class moves and taking a pupil off the roll
  • Invoices for the current session and term, manual payments, billed and collected totals
  • Attendance registers, CA and exam scores, and term-scoped report cards
  • A real timetable editor, the contact-form inbox, and owner-only users, roles and audit log

Student & parent · own record only

The portal

  • Results for the term, with the fee balance on the same screen
  • Pay an outstanding invoice from the portal, or let the bursary record cash or transfer
  • Timetable, homework and school notices
  • No route from the portal into /admin, for any account

The hard part

A fee must be recorded once, or not at all.

The one thing there was no room to get wrong was money. A parent double-clicking Pay must not be charged twice, a webhook arriving twice must not credit twice, and a payment that Paystack confirms late must not vanish. That constraint shaped the whole payment flow:

  1. One live checkout per invoice. Pressing Pay again returns the same checkout link for 30 minutes instead of opening a second live payment, so a double-click cannot charge the fee twice.
  2. The invoice is marked paid by a signed webhook. Paystack posts to the app with a request signed by the secret key, and nothing is credited until that signature checks out.
  3. The return trip asks Paystack directly. When the parent comes back, the portal queries that payment reference itself. If the webhook was delayed by a restart or a redeploy, the balance still updates.
  4. Retries are idempotent. Duplicate webhooks and the return check both run, and only the first one moves the balance.
  5. A late payment still counts. A checkout that timed out and was marked failed is credited if Paystack later confirms the money arrived.
  6. An overpayment is visible, not swallowed. Overpaying an invoice is rejected on the server; anything accidental is added in full and written to the audit log so the bursar can refund or carry it forward.

What this is not: a security review. The flow above is careful about duplicate and missing events, which is the failure a school actually meets. It has not been audited by anyone else, and I don't describe it as production-hardened beyond what it does.

The boring parts

The checks that don't show on a screenshot.

Most of the work in a system like this is invisible from the front page, and it is where the honest difference between a demo and something a bursar can use sits.

  • Every write goes through a server-side role check. Hiding a button is not the protection. Directory edits are limited to the owner, administrators, principal and vice principals; invoices and payments to the owner, administrators and bursar.
  • A disabled account, or a pupil taken off the roll, loses access on the next request — even if that person still holds an old session cookie.
  • The owner can download one JSON file holding every account, pupil, result, invoice and payment, and restore it inside a single database transaction: a damaged file is rejected and the current data is left untouched.
  • Backups are manual on purpose. The app hands over the file; it does not pretend to run unattended backups for the school.

Limits

What it doesn't do.

The project is live, but it is one school's system, built by one developer. These are the limits I would tell the next school before they compare it to an off-the-shelf package:

  • It is not multi-tenant. One deployment serves one school; a second school would need its own install and its own database.
  • Online payments need the school's own Paystack keys. With no keys set, the pay button is hidden and the bursary records payments by hand.
  • Backups are a button the owner presses, not a schedule. Whoever runs the school has to actually press it.
  • The demo accounts created on first setup must be given real passwords, or removed, before staff use it.
  • I'm a solo developer and this is the largest thing I've built. It has not had a professional security review, and for banking-grade requirements I'm not the right person.
